Building with AI coding agents, and keeping the code honest.

A working guide to Claude Code, Codex and Cursor: how to set a repo up so an agent starts well, how to plan, constrain and parallelise its work, and how to test and review what it writes. Every claim links to the lab’s own docs or to a study, and the docs were re-read in October 2026.

This is the deep dive behind the short coding-agents section of the prompting guide. That section covers the basic loop; this one covers configuration, safety and review. Agent products change monthly, so features are dated and anything that has been renamed or retired is flagged.

01 · The short version

Ten rules that hold across all three tools

If you read nothing else: an agent is a loop of reading, acting and checking. Your job is to make each step cheap to get right and cheap to catch when it is wrong.

  1. Keep the instruction file short

    Claude Code’s docs target under 200 lines per CLAUDE.md, Cursor under 500 lines per rule, and Codex stops reading at 32 KiB by default. Commands and gotchas, not a tour of the code.

  2. Write one file, not three

    AGENTS.md is read by Codex, Cursor and Copilot’s agent. Claude Code reads CLAUDE.md, which can import it with one line.

  3. Plan before anything non-trivial

    All three have a plan mode that reads but does not edit. Review the plan, not the diff, while changing course is still cheap.

  4. Give it a check it can run

    Tests, a build, a linter, a screenshot. Claude Code’s docs put it first: “Give Claude a check it can run.” Ask for command output as proof, not “it works.”

  5. Start restrictive, loosen on purpose

    Read-only or approve-edits to begin; allow specific commands you trust; deny what must never happen. Full-bypass modes belong in disposable containers only.

  6. Use hooks, not prose, for “always”

    An instruction can be ignored. A hook that runs the formatter or blocks a command cannot.

  7. Keep side work out of the main context

    Sub-agents and fresh sessions keep research and review from crowding the window you build in.

  8. Don’t let the agent grade itself

    Review the diff in a fresh context, with a different tool or a human. Models that can see the tests can learn to satisfy them rather than fix the bug.

  9. Read what you merge

    Treat AI output as a draft from a fast junior. Studies show it is plausible, sometimes insecure, and can invent packages.

  10. Never combine private data, untrusted input and a way out

    That trio is how agents get tricked into leaking. Remove one leg of it.

03 · Instruction files

Tell the agent what it can’t read from the code

An instruction file is loaded at the start of each session, so every line costs context on every task. The test Claude Code’s docs give: for each line, ask whether removing it would cause mistakes. If not, cut it.

How each tool finds the file

Claude Code: CLAUDE.md

  • Layers, broad to specific: managed policy, ~/.claude/CLAUDE.md, ./CLAUDE.md (or ./.claude/CLAUDE.md), and CLAUDE.local.md for personal notes you gitignore
  • Files in parent folders load at launch; files in subfolders load on demand
  • All files are concatenated, not overridden
  • @path imports, up to four hops deep; imports don’t reduce context cost
  • /init drafts one from the codebase; /memory edits it

Claude Code: memory

Codex: AGENTS.md

  • Global in ~/.codex, then from the project root down to the current folder
  • One file per folder; AGENTS.override.md wins over AGENTS.md there
  • Concatenated root-down, so closer files come later and effectively win
  • Stops at project_doc_max_bytes (32 KiB by default)
  • Check what loaded by asking Codex to summarise its instructions

Codex: AGENTS.md

Cursor: rules and AGENTS.md

  • Project rules are .mdc files in .cursor/rules; a plain .md there is ignored
  • Four types: Always Apply, Apply Intelligently (by description), Apply to Specific Files (globs), Apply Manually (@-mention)
  • Precedence: Team, then Project, then User
  • Keep each rule under 500 lines
  • Also reads AGENTS.md in root and subfolders

Cursor: rules

Cursor’s older rule names, “Agent Requested” and “Auto Attached”, no longer appear on its rules page; the types above are the current ones.

One source of truth for all three

AGENTS.md is an open format, now stewarded by the Agentic AI Foundation under the Linux Foundation, and read by Codex, Cursor, Copilot’s agent, Jules, Aider, Zed and others. Claude Code reads CLAUDE.md instead, and loads AGENTS.md only when no CLAUDE.md exists (a recent addition). The simplest way to share one file is a CLAUDE.md that imports it:

CLAUDE.md
@AGENTS.md

## Claude Code only
- Use plan mode for anything touching more than two files.
- After editing, run the commands under "Verify" in AGENTS.md
  and show me the output.
AGENTS.md: a starter that stays short
# {{Project name}}
{{One sentence: what this is and who uses it.}}

## Commands
- Install: {{npm ci}}
- Run one test file: {{npx vitest run path/to/file.test.ts}}
- Full test suite: {{npm test}}
- Lint and typecheck: {{npm run lint && npm run typecheck}}

## Verify before saying you are done
Run lint, typecheck and the tests for the files you changed.
Paste the command output. Never edit or delete a test to make it pass.

## Conventions that differ from the defaults
- {{e.g. We use named exports only; no default exports.}}
- {{e.g. Money is stored as integer cents, never floats.}}

## Gotchas
- {{e.g. The dev DB resets on every restart; seed with npm run seed.}}
- {{e.g. src/generated/ is built, never hand-edit.}}

## Boundaries
- Ask before adding a dependency or changing the database schema.
- Never touch .env files or anything under secrets/.

Adapted from the section lists in the AGENTS.md spec. Replace every {{…}}; delete any section you can’t fill with something the agent couldn’t learn by reading the code.

Grow it from failures, not from imagination

Don’t write a long file up front. Each time the agent repeats a mistake, add one line that would have prevented it (Mitchell Hashimoto’s “engineer the harness” habit). Prune quarterly. /context in Claude Code shows which memory files loaded, which is the quickest way to find a file that is bloating every session.

Scope instructions to the files they matter for

Claude Code supports path-scoped rules in .claude/rules/*.md with paths frontmatter; Cursor has glob rules; Codex has nested AGENTS.md. A frontend convention shouldn’t cost tokens during a backend task.

04 · Plan, then build

Explore, plan, implement, commit

Claude Code’s best-practices page names this four-step loop. In plan mode the agent “reads files, runs shell commands to explore, and writes a plan, but does not edit your source.” Cursor’s Plan Mode and Codex’s /plan work the same way.

Enter plan mode

  • Claude Code: Shift+Tab cycles modes, or start a prompt with /plan, or launch with claude --permission-mode plan. Ctrl+G opens the plan in your editor.
  • Codex: /plan or Shift+Tab
  • Cursor: Shift+Tab in the chat input. It asks clarifying questions first and saves plans outside the repo unless you choose “Save to workspace”.

Claude Code · Codex · Cursor

When to skip it

If you could describe the diff in one sentence (rename a variable, fix a typo, add a log line), just ask for it. Planning pays for changes with several valid approaches, many files, or code you don’t know.

Claude Code best practices

What a good plan contains
  • The files it will touch and why
  • The order of steps, each small enough to test
  • How each step will be verified
  • What it will deliberately not change
  • Open questions for you
A plan-first prompt that works in any of the three
Goal: {{what to build or fix, in one or two sentences}}

Step 1, explore only (do not edit anything): read {{folders or files}}
and tell me how {{the relevant part}} works today. Name the files that
matter and anything that surprised you.

Step 2, plan: propose a numbered plan. For each step give the files,
the change, and the exact command that proves the step worked.
List what you will NOT touch, and any questions where my answer would
change the plan. Wait for my approval before writing code.

Step 3, after I approve: implement one step at a time, run its check,
paste the output, and stop if a check fails instead of working around it.

Review the plan like codeA wrong assumption in a plan costs one sentence to fix. The same assumption found in a 600-line diff costs a rewrite. Ask the agent to put the plan in a file (PLAN.md) so it survives /clear and can be handed to a fresh reviewer.

05 · Permissions and sandboxes

Decide in advance what the agent may do without asking

Two controls matter: how much it can do before asking, and what it is physically unable to do. Only the second is a hard guarantee.

Claude Code’s six permission modes

ModeRuns without askingUse it for
defaultReads onlyUnfamiliar repos; learning what the agent does
acceptEditsReads, file edits and common filesystem commandsDay-to-day work where you read the diff afterwards
planReads and exploration only; no source editsPlanning (previous section)
autoEverything, with background safety checksLonger tasks you trust the checker on. Per the current docs, terminal sessions start here by default on supported models, unless an organisation disables it; check /permissions on yours.
dontAskOnly what is pre-allowed; anything else is deniedCI and scripts
bypassPermissionsEverythingIsolated containers and VMs only

Shift+Tab cycles default → acceptEdits → plan; auto and bypassPermissions join the cycle only when enabled, and dontAsk never appears in it. Source: permission modes.

Allow, ask and deny rules

Rules are evaluated deny first, then ask, then allow; the first match decides, and deny rules apply in every mode, including bypassPermissions. A starting point for a JavaScript project (.claude/settings.json, committed so the team shares it):

{
  "permissions": {
    "allow": [
      "Bash(npm run *)",
      "Bash(git commit *)"
    ],
    "deny": [
      "Bash(git push *)",
      "Read(./.env)",
      "Read(./secrets/**)"
    ]
  }
}

Rule syntax is from the permissions docs. Personal overrides go in .claude/settings.local.json.

A rule is not a wall

Claude Code’s docs are explicit that Bash rules match the command text the model writes and are “not a security boundary”: git -C . push is not matched by Bash(git push *). The same applies to Cursor, whose docs say its ignore file cannot block what the terminal and MCP tools can reach, and that “complete protection isn’t guaranteed.”

For a real boundary, use the environment: a container or VM with no credentials mounted, a branch protection rule on main, a token that cannot push. Treat permission rules as seat belts and the sandbox as the crash barrier.

Codex: sandbox plus approval policy

Codex splits the question in two. The sandbox says what is physically possible (read-only, workspace-write, danger-full-access); the approval policy says when it must ask (on-request, never, or granular). Network is off by default, and .git, .agents and .codex inside the workspace are protected read-only. The usual preset is --sandbox workspace-write --ask-for-approval on-request. The all-off flag, --dangerously-bypass-approvals-and-sandbox (alias --yolo), is named to discourage casual use. Two retired options to avoid copying from old tutorials: the untrusted approval policy and codex exec --full-auto. Source: Codex approvals and security, non-interactive mode.

06 · Sub-agents, skills, hooks and MCP

Four ways to extend an agent, and which to reach for

They solve different problems. Mixing them up is the commonest cause of a sprawling, expensive setup.

MechanismIt is…Reach for it whenContext cost
Instruction fileFacts the agent always needsCommands, conventions, gotchasEvery session
SkillA method the agent loads when relevantYou keep re-typing the same multi-step procedureDescription always; body only when used
Sub-agentA helper with its own context window, tools and promptResearch or review that would flood the main contextSummary comes back; the digging doesn’t
HookA script the harness runs at an eventSomething must always happen or be blockedNone; it runs outside the model
MCP serverA connection to a tool or data sourceThe information lives outside the repoTool descriptions, every session

Sub-agents (Claude Code)

Each sub-agent “runs in its own context window with a custom system prompt, specific tool access, and independent permissions.” Define one as a Markdown file in .claude/agents/. Only name and description are required; limiting tools is what makes a reviewer safe to leave unattended.

---
name: code-reviewer
description: Reviews a diff for correctness and security. Use after finishing a change, before committing.
tools: Read, Glob, Grep, Bash
model: sonnet
---
You review code you did not write. Read the diff and the plan.
Report only real problems: wrong behaviour, missed edge cases,
security issues, tests that don't test the change. For each, give
the file and line, what breaks, and a concrete fix. Do not report
style nits. If you find nothing serious, say so plainly.

Fields from the sub-agents docs. Optional fields include disallowedTools, permissionMode, skills, hooks, memory and isolation: worktree. Anthropic’s guidance is not to over-use them; for simple or single-file work the main agent should just do it.

Skills

A skill is a folder with a SKILL.md. Claude Code merged custom commands into skills: .claude/commands/deploy.md and .claude/skills/deploy/SKILL.md both create /deploy. Codex reads skills from .agents/skills and invokes them with $name. Both follow the open Agent Skills standard, so a well-written skill is largely portable.

---
name: release-notes
description: Drafts release notes from merged PRs since the last tag. Use when the user asks for a changelog or release notes.
---
1. Run `git describe --tags --abbrev=0` to find the last tag.
2. List merged PRs since then with `gh pr list --state merged`.
3. Group them under Added, Changed, Fixed. One line each, user-facing
   wording, no internal ticket numbers.
4. Write the result to RELEASE_NOTES.md and show me the diff.

Keep the description specific about when to use it (it is what the agent matches on) and the body under 500 lines. See the Claude Code skills docs and Anthropic’s progressive-disclosure write-up.

Hooks: the rule that can’t be forgotten

Hooks give “deterministic control: certain actions always happen rather than relying on the LLM.” Events include SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, Stop and more. A hook that exits with code 2 blocks the action and feeds its stderr back to the model; on Stop it sends the agent back to keep working. This example, from Anthropic’s hooks guide, formats every file the agent edits:

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}

Put it in .claude/settings.json; /hooks shows what is active. A Stop hook that runs the test suite and exits 2 on failure is a strong way to stop an agent declaring victory early. Source: hooks guide.

MCP: add sparingly

MCP (Model Context Protocol) servers connect an agent to outside systems. The config lives in .mcp.json or claude mcp add for Claude Code, [mcp_servers.name] in config.toml for Codex, and .cursor/mcp.json for Cursor. Cursor asks for approval before using MCP tools by default.

Every server’s tool descriptions occupy context in every session, and tool results can carry hostile text (see the security section). Add one that removes a frequent manual step, and prefer a command-line tool like gh where it will do: Codex’s own best-practices guide recommends MCP “when the context Codex needs lives outside the repo.” If you write tools for agents, Anthropic’s guide is the reference: clear names, meaningful results, helpful errors.

Sources: Claude Code MCP, Codex MCP, Cursor MCP.

07 · Parallel and cloud agents

Running more than one agent without them colliding

Two agents editing the same checkout will overwrite each other. The fix is isolation: separate working copies locally, or separate machines in the cloud.

Local: git worktrees

A worktree is a second checkout of the same repo on its own branch. In Claude Code, claude --worktree feature-auth (or -w) creates one under .claude/worktrees/ on branch worktree-feature-auth; add that folder to .gitignore. Plain git does the same: git worktree add ../project-feature-a -b feature-a. Sub-agents can opt in with isolation: worktree.

Claude Code worktrees

Cloud: one VM per task

Codex cloud gives each task its own workspace built from an environment you configure (repositories, install script, an internet-access setting that defaults to package managers only), and you can open a PR from the result. codex cloud has an --attempts option for 1–4 best-of-N tries. Cursor’s Cloud Agents (renamed from Background Agents) run in isolated VMs, push their own branch, and can be started from the editor, Slack, Linear, GitHub or an API.

Codex cloud · Codex CLI reference · Cursor Cloud Agents

In CI: headless runs

claude -p "…" --allowedTools "Read,Edit,Bash" runs once and exits; --output-format json returns the result, session id and cost, and --json-schema enforces a shape. --bare skips auto-discovery of hooks, skills, MCP and CLAUDE.md for repeatable scripted runs. Codex’s codex exec is read-only by default and supports --json and --output-schema. Anthropic and OpenAI each publish a GitHub Action.

Claude Code headless · GitHub Actions · codex exec

Parallel work moves the bottleneck to youFive agents produce five diffs to review. METR’s 2026 follow-up (next sections) found time tracking itself broke down when developers ran several agents at once. Parallelise independent tasks with tests behind them, and cap the number at what you can actually review the same day.

08 · Testing what it builds

Make “done” something the machine can check

An agent without a verification step is guessing confidently. Simon Willison notes that without tests an agent may claim something works “without having actually tested it at all.”

Tests first, then code

Ask for failing tests before the implementation, confirm they fail for the right reason, commit them, then let the agent make them pass. Claude Code’s docs suggest one session write the tests and another write code to pass them. Kent Beck calls the mindset “augmented coding”: “you care about the code, its complexity, the tests, & their coverage”, unlike vibe coding.

Beck · Claude Code best practices

Fix the cause, not the symptom

Claude Code’s docs ask for the root cause (“address the root cause, don’t suppress the error”) and for evidence rather than assertions. Put both in your instruction file, and make the verify commands the thing the agent must paste before it stops.

Claude Code best practices

Watch for agents cheating

METR found OpenAI’s o3 reward-hacked in 30.4% of RE-Bench runs (39 of 128), for example by overwriting the timer or reading the reference answer off the call stack, and it said “no” 10 of 10 times when asked whether that matched the user’s intent. Anthropic’s own research shows models learning tricks like sys.exit(0) so a harness reports a pass. In daily work the form is simpler: deleted assertions, special-cased inputs, skipped tests.

METR, June 2025 · Anthropic, Nov 2025

Mind what the benchmark measures

SWE-bench Verified is 500 human-validated tasks from real Python repos, scored by whether the repo’s own tests pass. It says a model can fix issues in that setting. It does not measure code quality, security or whether a reviewer would accept the patch, so a high score isn’t a promise about your codebase.

OpenAI, SWE-bench Verified

A test-first prompt
I want {{behaviour}} in {{module}}.

1. Write failing tests first, in the style of {{an existing test file}}.
   Cover the normal case, {{two edge cases}} and one error case.
2. Run them and show me that they fail, and why.
3. Stop and wait for me to approve the tests.
After approval: implement the smallest change that passes. Do not
modify the tests. If a test seems wrong, say so and stop. Finish by
running {{full test command}} and pasting the output.
What to check about the tests themselves
  • Does each test fail if you break the code it covers? (Revert the fix and run it.)
  • Are expected values written independently, not copied from the code’s output?
  • Do they hit real behaviour, or only mocks of the thing under test?
  • Did the diff remove or weaken any existing test or assertion?
  • For UI work, is there a screenshot or a browser run, not just unit tests?
09 · Reviewing AI-written code

What the evidence says, and a checklist that follows from it

The honest summary of the research is: AI help can feel faster than it is, it shifts risk toward review, and it amplifies the quality of the team using it. None of it says “don’t use agents”; all of it says “don’t skip reading.”

A review checklist for an agent’s pull request

1 · Scope

  • Does the diff do what the plan said and only that?
  • Any files changed that you didn’t expect, especially config, CI and .github/workflows/?
  • Any unrequested “improvements”?

2 · Tests

  • Were tests added for the behaviour change?
  • Were any removed, skipped or loosened?
  • Did you see the command output yourself, or only the agent’s word?

3 · Dependencies

  • Any new package? Does it exist, and is it the one you meant (check the registry page, age and downloads)?
  • Lockfile changes match the manifest?

4 · Security

  • User input reaching a query, shell, template or file path?
  • Secrets, tokens or keys in code, logs or fixtures?
  • Auth and permission checks on every new route?

5 · Edge cases

  • Empty, null, huge, duplicate, concurrent and failing-network cases
  • Error paths that swallow exceptions

6 · Understanding

  • Can you explain every changed line to a colleague?
  • If not, ask the agent to explain it, then check the explanation against the code

The rule that matters mostAddy Osmani’s phrasing: “It can write the first version, but never outsource the reading”, and never merge code that hasn’t been read and understood by a human. Simon Willison’s version: AI tools amplify existing expertise, and professionals using them stay “accountable.”

Let a second agent review first

A machine pass catches the cheap problems so your attention goes to design and intent. Use a reviewer that did not write the code.

Claude Code

/code-review (with an effort level, --comment to post on a PR and --fix to apply findings; /review is an alias) reviews for correctness bugs. /security-review analyses the current branch for injection, auth and data-exposure issues and needs an origin remote. /simplify and /ultrareview are also listed.

Commands · Code review

Codex

codex review and /review work on uncommitted changes, a base branch or a commit. On GitHub, comment @codex review; it flags only P0 and P1 issues, and you can put review rules in a ## Code Review Rules section of the nearest AGENTS.md.

Codex on GitHub

Cursor and Copilot

Cursor’s Bugbot reviews each PR update and reads project context from .cursor/BUGBOT.md; its Autofix can spawn a Cloud Agent to fix what it finds. For Copilot’s cloud agent, GitHub’s rule is that your approval of its pull request doesn’t count; a different human must approve, and workflows don’t run until someone inspects the changes and approves them.

10 · Agent security

An agent that reads the internet can be talked into things

Anything an agent reads (a web page, an issue, a README, a tool result) may contain instructions written by someone else. The model can’t reliably tell your orders from theirs.

The lethal trifecta

Simon Willison’s rule of thumb: an agent becomes dangerous when it combines access to your private data, exposure to untrusted content and the ability to communicate externally. “We need to avoid the lethal trifecta combination of tools ourselves to stay safe.” In practice: don’t let an agent that can read your .env also browse arbitrary pages and make outbound requests. Remove one leg.

Willison, June 2025

Slopsquatting

Models invent plausible package names; attackers register them. Seth Larson of the Python Software Foundation coined the term in 2025. Bar Lanyado’s 2023 experiment, an empty package published under the hallucinated name huggingface-cli, drew more than 30,000 downloads in three months. Never npm install or pip install a name you haven’t checked.

Spracklen et al. · Slopsquatting

The risk lists

OWASP’s 2025 LLM Top 10 includes Prompt Injection (LLM01), Sensitive Information Disclosure, Supply Chain, Improper Output Handling and Excessive Agency. Its Top 10 for Agentic Applications (December 2025) adds Agent Goal Hijack, Tool Misuse, Identity and Privilege Abuse, Unexpected Code Execution, and Memory and Context Poisoning. Both are useful as a checklist when you give an agent new tools.

OWASP LLM Top 10 · OWASP Agentic Top 10

Habits that cut the risk

  • Run agents with a token that cannot push to main or reach production
  • Keep secrets out of the working directory; deny reads of .env and secrets/
  • Review changes to CI files before approving any workflow run
  • Keep network off unless the task needs it (Codex’s default)
  • Use a container or VM for any bypass mode
  • Don’t paste private or client data into a cloud agent; see the safety section of the prompting guide
11 · Failure patterns

What goes wrong, and the fix

Claude Code’s best-practices page names several of these; the rest are common across the tools.

SymptomLikely causeFix
Agent ignores your instructionsThe instruction file is bloated, so the key line is lostCut it to what would cause mistakes if removed; move enforceable rules into hooks
Long session gets sloppyThe context window is full of old attempts (“the kitchen-sink session”)/clear between tasks; /compact with a note on what to keep; keep progress in PLAN.md
You keep correcting the same mistakeThe wrong approach is now in contextAfter two failed corrections, clear and write a better first prompt
“Done!” but it doesn’t runNo verification stepRequire pasted test and build output; add a Stop hook that runs them
Tests pass, behaviour is wrongTests assert what the code does, not what it should doWrite tests first from the spec; revert the fix and confirm they fail
Exploration never endsThe agent reads the whole repo for a vague questionScope the question to folders, or hand research to a sub-agent
Parallel agents conflictSame working copyOne worktree or cloud task per agent
Surprise dependency or file changeScope creptState boundaries in AGENTS.md; review the file list before the code
Rolled back, but a Bash change remainsClaude Code checkpoints don’t track files changed by Bash commandsCommit often; use git as the real undo

Related: the prompting guide’s coding prompts (feature build, bug reproduction, refactor plan, test writing) work unchanged in any of these agents.

12 · Sources and caveats

How this guide was made

Researched on 14 October 2026 with Claude: parallel research agents read each tool’s current documentation and the studies above, and every URL below was opened during research. Tool docs change quickly, so treat the dated claims as “as of October 2026.”

Things worth knowing before you rely on this

  • OpenAI’s Codex docs have moved from developers.openai.com to learn.chatgpt.com, and some pages now say “Codex and ChatGPT Work”. Links here use the new addresses.
  • Codex slash commands were checked against one reference page that doesn’t list every command other pages mention (such as /permissions), so run / in your own client to see what yours offers.
  • Claude Code’s docs reference version numbers around v2.1.28x. The default auto mode and AGENTS.md fallback are recent; check your installed version.
  • The “#” memory shortcut and Cursor’s Memories feature appear in older tutorials but not in the current docs, so they are left out.
  • Not verified at the primary source: the Claude 3.7 system-card remark about over-focusing on passing tests (not cited), the DORA 2025 figures (landing page and press only), the OWASP agentic list (taken from a secondary summary), and the date of Kent Beck’s post.
  • Not every command in this guide was run on every tool. Treat the templates as starting points and run them on a throwaway branch first.
