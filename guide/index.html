How to talk to AI so it does good work.

A working guide to prompting Claude, ChatGPT, Codex, Gemini and models you run yourself. It collects what the labs actually recommend, what the research says about popular tricks, 45 prompts you can copy, and a vetted shelf of repos and resources to hand to your AI.

Every recommendation links to its source. Model-specific advice changes fast; where a lab’s docs name a model, this guide says so, and where sources disagree, it says that too.

01 · The short version

Twelve rules that hold across every model

If you read nothing else. Each rule is backed in the sections below.

  1. Brief it like a smart new colleague

    Anthropic’s test: show your prompt to someone with no context. If they would be confused, the model will be too.

  2. Say what “done” looks like

    Describe the outcome, the success criteria and the shape of the output, not just the topic.

  3. Give the reason behind each rule

    “This will be read aloud, so no ellipses” works better than “NEVER use ellipses”. Models generalise from reasons.

  4. Show, don’t just tell

    Two to five varied examples beat paragraphs of description, especially for format and tone.

  5. Separate instructions from material

    Wrap pasted documents, data and examples in labelled tags like <document> so nothing gets mistaken for an instruction.

  6. Long material first, question last

    Anthropic and Google both recommend it; Anthropic measured up to 30% better answers on long inputs.

  7. Say what to do, not what to avoid

    “Write flowing paragraphs” beats “don’t use bullet points”. Image models especially draw what you name.

  8. Drop the shouting

    Newer models follow instructions closely. ALL-CAPS and “CRITICAL: MUST” now cause overreaction, not compliance.

  9. Let reasoning models reason

    With ChatGPT’s reasoning models, Claude’s thinking, or Gemini’s thinking levels, set the effort control instead of writing “think step by step”.

  10. Give it a way to check its work

    Tests, a command that must pass, quotes from the source. Checking against something real beats asking the model to double-check itself.

  11. Restart instead of patching

    Models get worse over long, corrected conversations. After two failed fixes, write one better prompt in a fresh chat.

  12. Treat outside content as untrusted

    Web pages, emails and documents can carry hidden instructions. Don’t combine private data, untrusted input and tools that send data out.

02 · Anatomy of a prompt

Six parts of a prompt that works

Not every prompt needs all six. A quick question needs one line. A task you will repeat, or hand to an agent, usually needs most of them. OpenAI suggests the order identity, instructions, examples, context; Anthropic and Google suggest putting long material before the final question.

1 · Goal and why

What you want, and what it is for. The purpose lets the model make sensible judgment calls.

2 · Context

Who it is for, what you already know, constraints, what has been tried.

3 · Material

Documents, data or code, each in its own labelled tag.

4 · Examples

A few varied samples of good output, wrapped in example tags.

5 · Output shape

Format, length, sections, tone; a schema for data.

6 · Done when

How to check the result, and what to do when unsure: ask, flag, or use a placeholder.

03 · Best practices

What the labs and practitioners agree on

The advice below appears in the official guides of at least one lab and is consistent with the others unless noted. Sources are linked on each item.

Clarity and context

Be explicit about ambition

Newer models do what you ask, precisely. If you want more than the minimum, say so: Anthropic’s example adds “Include as many relevant features and interactions as possible. Go beyond the basics.”

Anthropic best practices

Ask for action, not suggestions

“Can you suggest changes?” gets suggestions. “Change this function to…” gets changes. Word the request as the thing you want done.

Anthropic best practices

Describe the outcome, not every step

OpenAI’s current guidance: state the expected outcome, success criteria, allowed side effects and output shape, and avoid step-by-step process instructions unless the exact path matters. Older prompts over-specified because older models needed it.

OpenAI prompt guidance

Explain the why

A rule with a reason generalises to cases you didn’t foresee. A bare rule gets applied too literally or not at all. Anthropic recommends heuristics at the “right altitude” over brittle if-then lists.

Anthropic, context engineering

Avoid vague quantities

Mistral’s guide flags “too long”, “many”, “few”, “better” as words that blur instructions. Give numbers: “under 150 words”, “three options”.

Mistral prompting guide

Hunt for contradictions

Conflicting instructions are worse than missing ones. OpenAI says they are “more damaging” to GPT-5-class models, which burn effort reconciling them. Claude may pick one at random.

GPT-5 prompting guide · Claude Code memory

Structure and examples

Use tags as delimiters

Put each kind of content in its own descriptive tag (<instructions>, <context>, <document index="1">). Works for every vendor. Google’s advice: pick XML or Markdown and stay consistent.

Anthropic · Google

Few, varied, canonical examples

Anthropic: 3–5 examples. Google: “always include few-shot examples”, in a consistent format. Vary them so the model copies the pattern, not the surface details.

Google prompting strategies

Balance your examples

Example order and label mix can swing accuracy wildly; models lean toward the majority label and the most recent example. Mix the classes and shuffle the order.

Zhao et al., Calibrate Before Use

Match your prompt to your output

A prompt full of bullets gets bullets back. Anthropic notes that removing Markdown from your prompt reduces Markdown in the answer.

Anthropic best practices

Use structured outputs for data

When you need JSON, use the API’s structured-output or JSON-schema mode (OpenAI, Gemini, Ollama, llama.cpp grammars) rather than only describing the schema in words.

Ollama structured outputs · Google

Static first, variable last

Put reusable instructions at the top and the changing part at the end. It reads better and lets providers cache the repeated prefix, which cuts cost and latency.

OpenAI prompt engineering

Long documents and accuracy

Documents on top, question at the bottom

Anthropic measured up to 30% better answers with the query at the end of long, multi-document prompts. Google recommends the same: “Based on the information above…”.

Anthropic · Google Gemini 3

Quote first, then answer

Ask the model to pull the relevant passages into <quotes> before answering from them. It focuses attention and makes the answer checkable.

Anthropic best practices

Let it say “I don’t know”

Give explicit permission and a format for uncertainty: “If the documents don’t say, answer ‘not stated’”, or “[TK: missing fact]” placeholders in drafts. Meta’s Llama guide and OpenAI both recommend it.

Meta Llama guide · OpenAI

More context is not free

Chroma tested 18 models and found performance drops as input grows, even on simple tasks, and distracting text makes it worse. Include what’s relevant, not everything you have.

Chroma, Context Rot

Make the context the source of truth

Gemini 3 may fall back on training knowledge when your material conflicts with it. Say plainly that the provided text wins, especially for fiction, hypotheticals or recent facts.

Google Gemini 3 guide

Use code for exact work

Models are weak at arithmetic and counting but strong at writing code. Ask for a script or a spreadsheet formula and run it, rather than trusting mental math.

Meta Llama guide · Mistral

Process

Chain steps you need to inspect

Draft, review against criteria, then refine, each as its own step. Anthropic lists five workflow patterns (chaining, routing, parallel, orchestrator-workers, evaluator-optimizer) and says to use the simplest that works.

Building effective agents

Let it interview you

For fuzzy, open-ended work, ask the model to question you first, then write a spec. For well-defined tasks, skip it: OpenAI warns newer models can stop too early if told to always ask.

Claude Code · OpenAI

Test prompts on real cases

Before you rely on a prompt, run it on a set of real inputs and read the outputs. Hamel Husain calls error analysis “the most important activity in evals”: look at 100 outputs, then write pass/fail checks.

Hamel Husain, evals FAQ

Start minimal, add on failure

Begin with the shortest prompt that could work on the best model, then add instructions only for failures you actually observe. Anthropic and OpenAI both recommend a “fresh baseline” when moving to a new model.

Anthropic · OpenAI

Have the AI improve your prompt

Ask the model to critique your prompt, then rewrite it, then propose test cases. Anthropic’s Console and OpenAI’s Playground both have prompt generators and optimizers built in.

Anthropic prompt improver · OpenAI

There are no secret prompts

Ethan Mollick’s point holds: working with the AI over a few turns, and giving it real context, matters more than any magic phrasing.

04 · Tricks vs evidence

What the research says about popular tricks

Plenty of prompting folklore comes from 2023-era models. Here is how the common tricks hold up in more recent testing.

TrickVerdictWhat the evidence shows
“Think step by step”Model-dependentIt made a big difference in 2022 (Kojima et al.: 17.7% → 78.7% on one maths set). Wharton’s 2025 tests found modest gains for non-reasoning models and almost none for reasoning models, with 20–600% more latency (Prompting Science Report 2). OpenAI says it can hurt reasoning models (reasoning best practices). Use the effort or thinking setting instead.
“You are a world-class expert…”Tone, not accuracyExpert personas generally did not improve factual accuracy across six models (Wharton Report 4). Roles still shape voice and focus (Anthropic), and Gemini 3 follows personas so closely they can override other instructions (Google). Pair a role with real context.
Tipping or threateningUnreliableSmall, mostly insignificant average effects, with individual questions swinging up to 36 points either way (Wharton Report 3).
Rudeness or extreme politenessSmall, inconsistentOne study found rude prompts slightly better on GPT-4o (Mind Your Tone), on only 50 questions; follow-ups found effects vary by model and subject. Write clearly and neutrally.
ALL-CAPS and “CRITICAL”Now counterproductiveAnthropic says newer models overreact to aggressive emphasis; write “Use this tool when…” instead (best practices). OpenAI reserves ALWAYS/NEVER for true invariants. In CLAUDE.md, “if you emphasize many lines, none of them stands out” (Claude Code).
“Double-check your answer”Needs a real checkWithout outside feedback, models often change right answers to wrong ones (Huang et al., ICLR 2024). Self-correction works when there is something real to check against: tests, code execution, sources, or a fresh reviewer.
Majority vote over several answersWorks, costs moreSelf-consistency (sample several reasoning paths, take the most common answer) gave large gains on reasoning benchmarks (Wang et al.). Worth it for high-stakes single answers.
Correcting a chat over and overStart freshAcross 15 models, performance dropped about 39% on average when requirements arrived over many turns instead of one complete prompt (Laban et al.). Consolidate and restart.
05 · Model by model

Where the labs’ advice differs

The fundamentals transfer, but each family has quirks. These notes come from each lab’s own documentation as of October 2026. Anthropic’s caveat applies everywhere: effects measured on one model should be re-checked before you rely on them with another.

Anthropic

Claude

  • Trained for precise instruction-following: ask explicitly for “above and beyond” work, and phrase requests as actions.
  • XML tags are the recommended way to structure prompts; long documents go on top.
  • Thinking is controlled with adaptive thinking and an effort setting; on the newest models it is always on. Rely on it rather than asking for reasoning in tags. A general “think thoroughly” beats a hand-written step plan.
  • Pre-filling the start of Claude’s reply is no longer supported from the 4.6 generation; put format instructions in the prompt instead.
  • Newer models are terse by default and may skip summaries; ask for one if you want it. Opus 5 is an exception and runs long.
  • The docs include ready-made blocks for common behaviours: act by default, ask before acting, avoid over-engineering, and avoid generic “AI-looking” front-end design.

Best practicesPublished system promptsTutorial

OpenAI

ChatGPT and the GPT API

  • Reasoning models are like a senior colleague: give the goal. Non-reasoning models are like a junior one: give explicit steps.
  • Current guidance is outcome-first: success criteria, allowed side effects, evidence rules, output shape. Start from a fresh baseline when moving to a new model rather than carrying old prompt stacks forward.
  • Use reasoning effort (start at medium; higher is not automatically better) and verbosity controls instead of prompt tricks.
  • Reasoning models don’t need “think step by step” and often don’t need examples; try zero-shot first.
  • Ask for approval only after preparing something concrete to review. Put tool-specific guidance in tool descriptions.
  • In long chats, formatting instructions fade; the GPT-5 guide suggests re-stating them every few messages.

Current model guideReasoning modelsCookbook

OpenAI

Codex

  • Write tasks in four parts: goal, context, constraints, and “done when”.
  • Plan first (/plan) for anything non-trivial; keep a PLANS.md for long work.
  • Require verification: run lint and the smallest relevant tests, and report the commands and results.
  • AGENTS.md layers global, repo and folder files; the nearest one wins. “A short, accurate AGENTS.md is more useful than a long file full of vague rules.” Add rules only after repeated mistakes.
  • If you keep repeating the same prompt, turn it into a skill. OpenAI notes that its newest models need less hand-holding: overly specific guidance can now hurt.

Codex best practicesAGENTS.md guide

Google

Gemini

  • Google recommends always including few-shot examples, with a consistent format.
  • Gemini 3 is concise by default and responds best to direct instructions; avoid “overly persuasive language”. Ask for detail explicitly.
  • Order: context first, then the task, then constraints and format, with the critical restriction on the last line.
  • Don’t lower the temperature on Gemini 3: Google recommends the default of 1.0 because lower values can cause looping. On the newest Gemini models, remove sampling settings entirely.
  • Use thinking level rather than token budgets. Avoid sweeping bans like “do not infer”, which can break basic reasoning; scope them instead.
  • In Gemini CLI, standing instructions go in GEMINI.md; it can be set to read AGENTS.md too.

Prompting strategiesGemini 3 guideCookbook

Open weights

Local models: Llama, Qwen, Mistral and friends

  • Use the model’s exact chat template. Hugging Face warns that the wrong control tokens make models “drastically worse”. Ollama and LM Studio handle this for you if the model is set up correctly.
  • Smaller models need the explicit, example-backed style: a role, rules, clear instructions and one example (Meta’s Llama guide). Terse, goal-only prompts suit frontier reasoning models, not 7B models.
  • Use the model card’s sampling settings. Qwen3 thinking mode: temperature 0.6, top-p 0.95; and “do not use greedy decoding”, which causes endless repetition.
  • Qwen3 thinking can be toggled with /think and /no_think; keep only final answers in chat history.
  • Check the context length (Ollama’s num_ctx); if it is too small, long system prompts are silently cut off.
  • Force structure with JSON Schema or grammars (Ollama format, llama.cpp GBNF), and describe the structure in the prompt as well.

Llama guideQwen3Mistral guideOllama Modelfile

Media models

Images, music and video

  • Images: describe subject, action, setting, composition, lighting and style in full sentences. Put any text that must appear in quotes, with its position and typeface (OpenAI, Google).
  • Name what you want, not what you don’t: “no cake” can still produce cake. Use Midjourney’s --no or an exclude field instead.
  • For edits, say “change only X” and list what must stay the same. Repeated edits drift, so restate it each time.
  • Midjourney: short, specific prompts often work best; use exact counts and specific words (“enormous”, not “big”).
  • Suno: describe style in a few descriptors, use the Exclude field for unwanted elements, and adjust the Weirdness and Style Influence sliders. Section tags like [Chorus] are community practice, not official.

06 · Coding agents

Working with Claude Code, Codex, Gemini CLI and Cursor

With agents, the prompt is only part of what the model sees. Anthropic calls the bigger skill context engineering: curating the smallest set of high-signal information for each step. Claude Code’s docs put it bluntly: the context window “fills up fast, and performance degrades as it fills.”

Context files: standing instructions for your repo

ToolFileHow it loads
Claude CodeCLAUDE.md, .claude/rules/*.mdEvery session; supports @path imports. Aim for under 200 lines per file. Docs
Codex, Cursor, Copilot, Jules, Aider, Zed and moreAGENTS.mdOpen format; nested files allowed, nearest one wins. agents.md
Gemini CLIGEMINI.mdGlobal, project and folder files are all combined; can be pointed at AGENTS.md. Docs
Cursor.cursor/rules/*.mdcAlways, by file pattern, when relevant, or on request. Docs
GitHub Copilot.github/copilot-instructions.mdRepo-wide, plus path-scoped instruction files. Docs

Put in

  • Exact build, single-test, lint and typecheck commands
  • Conventions that differ from the defaults
  • Environment quirks and gotchas
  • How to verify work is done

Leave out

  • Anything the agent can learn by reading the code
  • File-by-file tours and long tutorials
  • Things that change often
  • Walls of NEVER/ALWAYS

Maintain it

  • For each line ask “would removing this cause mistakes?”
  • Add a rule each time the agent repeats a mistake (Hashimoto)
  • Use hooks, not prose, for anything that must always happen

Why it mattersClaude Code’s docs warn that “bloated CLAUDE.md files cause Claude to ignore your actual instructions”. A short, accurate file beats a long one.

The working loop

Explore, plan, then build

Have the agent read and explain first, write a plan you approve, then implement. Use plan mode (Claude Code: Shift+Tab; Codex: /plan). Skip the plan if you could describe the change in one sentence.

Claude Code best practices

Give it a check it can run

Tests, a build, a screenshot comparison. Claude Code calls this the difference between a session you watch and one you can walk away from. Ask for the command output as evidence, not a claim of success.

Claude Code · Codex

Don’t let it game the tests

Anthropic’s guidance includes: “Tests are there to verify correctness, not to define the solution,” and it is unacceptable to remove or edit tests to pass.

Anthropic best practices

Review in a fresh context

Use a sub-agent or a new session to review the diff against the plan, so the agent doing the work isn’t grading itself. Ask it to report only real gaps; chasing every nit leads to over-engineering.

Claude Code

Keep sessions short

Clear between unrelated tasks. After two failed corrections, clear and write a better first prompt. Compact with a note about what to keep. For long work, keep progress in files and use git as checkpoints.

Claude Code · Codex

Use sub-agents for side quests

Send research and exploration to sub-agents so the main context stays clean. Don’t overuse them: for simple, sequential or single-file work, the main agent should just do it.

Anthropic

Turn repeated prompts into skills

A skill is a folder with a SKILL.md whose description loads up front and whose body loads only when relevant. Keep the body under 500 lines and write the description in the third person, saying what it does and when to use it.

Skills best practices · agentskills.io

Add tools sparingly

Every MCP server’s tool descriptions cost context. Start with one or two that remove a frequent manual task. Command-line tools like gh are often the most context-efficient option.

Codex · Claude Code

Write tools like you’d brief a new hire

Clear names and parameters (user_id, not user), readable results instead of opaque IDs, sensible pagination, and error messages that say how to fix the call. Make mistakes hard: Anthropic fixed a class of errors by requiring absolute file paths.

07 · Prompt library

45 prompts worth copying

Each one works in Claude, ChatGPT, Gemini or a local model. Replace the {{placeholders}}, delete what you don’t need, and keep the parts that say what “done” looks like. Where a prompt adapts a public source, the source is linked.

Coding · 01

Interview me, then write the spec

Adapted from Claude Code best practices (“let Claude interview you”). Mirrors GitHub Spec Kit’s specify → plan → build flow.

I want to build {{brief description of feature}}.

Interview me in detail before writing any code. Ask about technical implementation, UI/UX, edge cases, failure modes, security, and tradeoffs. Skip obvious questions; dig into the hard parts I may not have considered. Ask a few questions at a time.

When we've covered everything, write a self-contained spec to {{SPEC.md}} that:
- names the files, modules and interfaces involved
- states what is explicitly OUT of scope
- lists acceptance criteria as checkable statements
- ends with an end-to-end verification step that proves the feature works
Do not start implementing.

Then start a fresh session to build from SPEC.md, so the builder starts with clean context.

Coding · 02

Feature build: goal, context, constraints, done when

Structure from OpenAI Codex best practices.

Goal: {{what to change or build, one or two sentences}}
Context: {{files, docs, error output, an existing pattern to follow, e.g. "follow the pattern in src/widgets/HotDogWidget.tsx"}}
Constraints: {{stack rules, "no new dependencies", security requirements, files you must not touch}}
Done when: {{tests that must pass, a command that must succeed, observable behavior}}

Work in small steps. After implementing, run {{test/lint/typecheck commands}} and show me the actual output. If something blocks you, stop and tell me rather than working around it.
Coding · 03

Reproduce a bug and find the root cause

Grounded in Claude Code best practices: write a failing test first; fix the cause, don’t suppress the error.

Bug: {{symptom as users see it}}
Evidence: {{error message / stack trace / logs, pasted verbatim}}
Where I suspect it lives: {{path or "unknown"}}
Expected vs actual: {{...}}

1. Before changing anything, read the relevant code. Don't speculate about code you haven't opened.
2. Write a minimal failing test (or script) that reproduces the bug. Run it; show it fails.
3. List 2-4 candidate root causes, with the evidence for and against each.
4. Fix the root cause. Do not suppress the error, special-case the test, or catch-and-ignore.
5. Re-run the reproduction and the surrounding tests; show the output.
6. Explain in 3 sentences why the bug happened and why the fix is correct.
Coding · 04

Code review that reports only what matters

From the writer/reviewer pattern in Claude Code best practices. Works best in a fresh chat or sub-agent.

Review {{the diff on this branch vs main / a file / a PR}} for correctness.
Context: the change is meant to {{intent}}. Our conventions: {{link or file}}.

Report only findings that affect correctness, security, data integrity, or the stated requirements. For each: file:line, what goes wrong, a concrete input or scenario that triggers it, and a suggested fix. Rate confidence (high/medium/low).
Do NOT report style preferences or speculative "could be cleaner" items.
If you find nothing significant, say so plainly. That is an acceptable answer.
Coding · 05

Check the work against the plan

Closely follows Claude Code best practices.

Use a sub-agent (fresh context) to review the {{feature}} diff against {{PLAN.md / SPEC.md}}.
Check that every requirement is implemented, every listed edge case has a test, and nothing outside the task's scope changed. Report gaps, not style preferences.
Coding · 06

Refactor plan, no code yet

I want to refactor {{module/area}} because {{the pain: duplication, slow tests, hard to extend for X}}.

Read the code first. Then produce a plan, not code:
- Current structure (short), and the specific problems, with evidence (file:line)
- Target structure and why it solves those problems
- A sequence of small, independently shippable steps; each keeps tests green
- For each step: files touched, risk, how we verify behavior is unchanged
- What you would NOT change, and why
Keep it simple. Don't introduce abstractions for one-time operations.

The last line echoes Anthropic’s guidance against over-engineering.

Coding · 07

Write tests that test the code, not the other way round

Grounded in Claude Code and Anthropic’s guidance against gaming tests.

Write tests for {{function/module}} using {{framework}}, following the style of {{an existing test file}}.
Cover: the happy path, {{specific edge cases}}, invalid inputs, and boundary values.
Prefer real objects over mocks unless {{external service}} is involved.
Each test name should state the behavior being checked.
Run the tests and show the output. If a test fails because the CODE is wrong, report it. Do not change the assertion to match buggy behavior.
Coding · 08

Plan, then execute (for coding agents)

Based on Claude Code’s explore → plan → implement flow and Mitchell Hashimoto’s separate planning and execution sessions.

Phase 1, explore (read only, make no edits): read {{dirs/files}} and explain how {{the relevant subsystem}} currently works.
Phase 2, plan: write a step-by-step plan to {{goal}} in PLAN.md: files to change, order of changes, tests to add, risks, and a verification command for each step.
Stop and wait for my approval.
Phase 3, after I approve: implement step by step, ticking items off in PLAN.md and running the verification after each step. If reality diverges from the plan, update the plan and tell me before continuing.
Coding · 09

Explain a codebase to me

Grounded in Simon Willison on using LLMs for code.

I'm new to this codebase and need to {{goal, e.g. add an API endpoint}}.
Give me:
1. A 10-line overview: what it does, main entry points, how a request or data flows.
2. A map of the 8-12 most important files/dirs and the role of each.
3. How {{a specific subsystem: auth / logging / config}} works, with file:line references.
4. Where I'd make my change, and which existing code is the best pattern to copy.
5. Surprises and gotchas you noticed.
Only state what you verified by reading code; mark guesses as guesses.

08 · Safety

Prompt injection, in plain terms

When an AI reads a web page, an email or a document, any instructions hidden in that text can steer it. This is the top risk on the OWASP list for AI apps, and Simon Willison notes there is still no 100% reliable fix.

Know the lethal trifecta

Danger comes from combining three things: access to private data, exposure to untrusted content, and a way to send data out (web requests, email, links). Remove any one leg.

Simon Willison

Keep outside text in its lane

Pass untrusted text as clearly tagged material, never as instructions. Between agent steps, use fixed formats (enums, schemas) instead of free text.

OpenAI agent safety

Approve risky actions

Let agents take reversible, local actions freely, but require approval for anything destructive or shared: deleting, force-pushing, sending, paying. Anthropic’s docs include a ready-made prompt for this.

Anthropic

Vet skills and MCP servers

A skill or tool server is code and instructions you are handing your agent. Install from trusted sources and read the scripts first.

Anthropic on skills

Don’t put secrets in prompts

System prompts leak: whole repositories collect extracted ones. Assume anything in a prompt can be read by a determined user.

Example collection

Test your own app

If you build with AI, scan it before others do. promptfoo, garak and PyRIT probe your own system for injection and leakage.

How to feed a repo to your AIFor a chat AI, paste the one file you need (a Fabric pattern, a CLAUDE.md example) rather than the whole repo. For coding agents, install skills into the tool’s skills folder, or clone the repo next to your project and ask the agent to read the specific files. For whole-repo questions, tools like Simon Willison’s llm let you pipe files into a prompt.
